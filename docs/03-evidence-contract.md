# 主张、证据与检查契约

当前已实现项目与八类记录的结构契约及只读校验器，Schema 兼容字段为 `0.1`。这是研究数据格式的身份，不是多份软件发行版。定义见 `core/model.py`，同源生成的 JSON Schema 位于 `core/schemas/`。这里只验证结构、引用和文件身份，不对学科方法或科学判断作自动认证；不沿用个人包固定 12／14 列接口作为通用标准。

## 对象与最小字段

| 对象 | 最小内容 | 按需增加 |
|---|---|---|
| Project | ID、问题或目标、当前范围 | 学科、方法、文类、资源、治理与期刊配置 |
| Activity | ID、下一项行动、输入和产物引用、进度 | 前置依赖、预算、执行记录、跳过或变更理由 |
| Source | ID、外部或既有材料的身份、定位与版本 | 元数据、实际访问状态、权利与可获得性 |
| Statement | ID、表述、种类、范围与版本 | 假设、角色、依赖、评估、稿件位置 |
| Evidence | ID、材料类型、来源／生成方法、定位与版本 | 指纹、访问限制、质量限制、校准或采集信息 |
| Decision | ID、选择、理由、责任主体和时间 | 已考虑备选项、证据引用、后果与重新评估条件 |
| Artifact | ID、类型、位置与版本 | 生成来源、检查记录、共享范围 |

Source 回答材料是什么，Evidence 回答本次研究实际使用或生成了什么、如何形成，Decision 回答为何据此作出某项选择。文献存在、材料支持一项主张与研究者决定推进是三件不同的事实。新生成的证据可以记录生成活动而无外部 Source。

Source 的书籍版次、档案号、页码、馆藏索引、数据版本或网页访问日期按材料选择，不要求每项具备 DOI。访问不到的全文可以登记为未读，不能声称完成内容核对。

Statement 的种类可为 `question`、`formal`、`empirical`、`interpretive`、`normative`、`design`。`question` 的支持评估通常不适用；可以关联动机或相关材料，但不将问题本身判为真假。角色如贡献、背景、前提、探索性结果、负结果、猜想或开放问题，独立于种类。类型与角色允许方法适配器有版本地扩展。

## 证据关系不是简单计数

Statement 与 Evidence 之间单独记录关系：`supports`、`qualifies`、`challenges`、`contextualizes`、`derived_from`，附上关系理由、涉及的子主张和限制。同一材料可以支持一项解释、挑战另一项解释；不能按链接数或投票数自动升格结论。

主张依赖另行登记，并区分实际论证支撑与单纯背景引用。某个条目从稿件清单排除后，如果结论仍实际依赖它，其核查义务仍然存在。条件性结论可以保留未证前提，但必须按其方法明确呈现为前提，不能当作已经独立确立的支持。

受限证据可用安全的来源 ID 和受控访问说明定位；普通检查验证登记及访问说明是否完整，不强迫公开原件。公开来源索引与私密路径映射分开，避免通过文件名、访谈编号或日志泄露身份。

## 五个正交维度

| 维度 | 拟议状态 | 含义 |
|---|---|---|
| 工作进度 | `draft`、`in-progress`、`reviewed`、`archived` | 只描述工作，不代表主张成立 |
| 证据评估 | `not-assessed`、`supported-in-scope`、`mixed`、`challenged`、`insufficient`、`not-applicable` | 由有范围说明的评估产生；不足不等于为假 |
| 形式核验 | `not-applicable`、`not-started`、`partial`、`complete-in-scope` | 仅用于适用命题，注明系统、对象、假设与覆盖范围 |
| 本次产物用途 | `included`、`background`、`excluded` | 不改变科学状态或实际支撑依赖 |
| 必要要求 | 适用性 `unknown`／`applicable`／`not-applicable`，加处理记录 | 记录依据、责任主体和文件，不凭自填状态自动认证批准 |

数值观察、解析证明、形式检查、实验材料、史料、访谈和概念论证保留材料类型。类型本身不是统一质量排名；一次有效范围内的形式检查也不会自动验证现实模型。

每份评估注明对象及版本、适用方法、评估人或代理、检查范围、依据、结果和未覆盖内容。代理可以生成评估草稿，但不能伪装为伦理委员会、临床专家或独立人类审稿人的确认。

方法绑定单独记录 `method_id`、`profile_version`、`variant`、`applies_to` 与 `reason`。`applies_to` 引用相关主张、活动或材料；变体归属于相应方法，不能只在项目中列一个无所属关系的变体字符串。`applies_to` 使用带类型前缀的引用列表（例如 `statement:S1`、`activity:A1`），只检查其存在及方法变体归属。宿主按当前任务读取适用的方法指导执行具体检查，CLI 仍不自动核验论证内容。

核心支持工作进度、评估与形式核验的显式登记，以及项目级治理适用性；详细审批文件、科学方法与目标场所核验尚未实现。登记者填写的评估文字不会被程序提升为自身认证。

## 分开输出五类检查

| 检查维度 | 可以报告 | 不得自动推出 |
|---|---|---|
| 登记与接口 | ID、字段、关系、路径与版本一致 | 研究结论成立 |
| 方法与论证 | 具体证明、识别、测量或解释检查的有界结论 | 全文正确或穷尽新颖性 |
| 治理与权利 | 适用性、材料记录、待决事项和责任主体 | 机构审批、合法性或知情同意自动获批 |
| 执行与复现 | 命令、版本、输出和失败／超时 | 运行成功就是科学验证 |
| 场所与交付 | 当前目标要求、附件、版式与声明对应情况 | 接收、发表或自动投稿 |

检查结果采用 `pass`、`fail`、`not-assessed`、`not-applicable`、`needs-human-review`，始终附带维度与范围。不设置一个笼统的“论文已通过”总开关。材料不齐可以阻止某项行动或完整性检查，但不禁止诚实地讨论开放问题、做局部编辑或交付阶段性报告。

## 格式与兼容

项目的权威格式为 UTF-8 JSON：`project.json` 保存配置，`records/registry.json` 保存登记与恢复状态。`PROJECT.md` 是独立作者笔记，恢复命令可输出只读 Markdown 摘要，不反向覆盖 JSON；CSV 导入导出尚未实现。项目和登记簿记录 schema 版本，记录封装另有递增版本及历史；更新需显式指定目标记录版本，避免静默覆盖。

后续个人包旧台账兼容计划采用显式、只读试转换（当前尚未实现）：生成字段映射和未映射报告，再写入新项目的副本；保留原版本、原状态文字与限制。旧 `proved` 或 `numerical-supported` 不应直接映射成通用的“科学有效”，无法安全映射时保留未知并要求审阅。转换器不改写原个人项目。
