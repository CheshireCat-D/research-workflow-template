# 中文学位论文和毕业设计交付

从学校当届文件确定院系、学位类型、答辩或存档阶段以及实际提交对象。记录正式模板或通知的文件名、版本、具体页码或条款。将封面、双语摘要、附录、声明、匿名送审稿等逐项对应到适用条款。遇到相互冲突的条款，留下两处原文位置和待确认的问题；能独立完成的部分继续进行。

## 整理稿源

以作者确认的可编辑稿为主源。对每种材料记下允许用途，例如学校模板管格式，样稿只借鉴目录，实验记录支持具体数值。学校指定的资料也要核实能否支持正文所述结论。引用核验可沿用 [RWT 文献工作流](../../rw-literature/SKILL.md)；数字顺序制按指定体例检查首次出现、复引同号、区间以及参考文献表的双向对应。数字编号检查与逐条阅读原文分别留下结果。

学校要求中英文摘要时，逐项对应样本或定理范围、变量定义、主要结果、单位及限制。保留两种语言各自准确的表述，用两份摘要中各自的一句实际结论作机器可核的锚点。论文本身使用“将来完成”的设计说明时，不改写成已经获得的数据。导师修订意见保留位置、处理结果和验证记录；换年度或院校时重新从当届要求判断适用范围。

## 实际交付检查

可直接使用现有的项目清单。需要对照 DOCX 与 PDF 时，把[最小示例](../assets/thesis-delivery.example.json)复制到材料目录，替换为本项目的要求依据、文件名与实际文字。命令中的 `WRITING` 表示这次使用的 `rw-writing` 目录。清单中所有文件路径相对于清单本身，工具只读本地文件，将 JSON 打印到终端。

```sh
python3 WRITING/scripts/check_thesis_delivery.py /path/to/project/thesis-delivery.json
```

| 清单内容 | 检查方式 |
|---|---|
| `institution`、`degree`、`basis` | 记录适用学校和学位，以及所用要求文件的 SHA-256 和条款位置；条款内容及优先级由研究者阅读。 |
| `docx`、`pdf` | 从实际 DOCX 正文段落提取文本，读取实际 PDF 的文本层。使用本机 `pdftotext` 或当前 Python 中的 `pypdf`。无法取得文本时保存待核状态。 |
| `anchors` | 每个 `label` 唯一。`text` 是要在两个版本中找到的原文片段，返回 PDF 匹配页码。可附对应段落的显式 Word 样式 ID，如 `"style": "Heading1"`。字号、样式继承、页眉、脚注、公式、图片、跨页断句和语义等价仍需专门复核。短片段应选有区分度的内容，以免目录或重复段落命中。 |
| `materials` | 每条记录说明文件用途和选用依据。`applies: true` 的材料核实存在并记录指纹；`false` 表示已有依据不适用；`null` 记录适用性尚未决定。角色、附件数量和学校要求均由当前项目决定。 |
| `section_order` | 可选的学校指定章节顺序，如 `["摘要", "Abstract", "绪论", "参考文献"]`。在 DOCX 正文段中按完整标题比对，缺失或逆序标为不匹配。目录与正文同名等多次命中时转人工定位。 |
| `numbered_references` | 可选的数字方括号顺序制。给出唯一的正文起始标题、参考文献标题，若书目之后还有附录则给出终止标题。核对正文首次出现次序、重引、缺失书目和书目显式编号；支持逗号、顿号及闭区间。自动编号、作者年份制、脚注、公式中的数字区间、参考文献真实性等需要结合原稿核对。 |
| `visual_review` | 可选的版面查验记录。实际从最终可编辑文件导出 PDF，逐页看完后再填写；文件版本改变、只看过部分页面或发现尚未解决的问题会反映在结果中。 |

例如正文以“绪论”开始、书目位于“附录”前，可增设以下片段。若提供 `sources`，核对每个显式书目号是否有对应记录。`original_checked` 表示研究者记录了原文位置；`metadata_only`、`unavailable` 和未配对条目标为待核。编号工具只检查台账及文中序号，逐处论点核验沿用 `rw-literature`。示例中的说明文字需要替换。

```json
"numbered_references": {
  "body_heading": "绪论",
  "reference_heading": "参考文献",
  "end_heading": "附录",
  "sources": [
    {"number": 1, "origin": "实际文献的标识或路径", "status": "metadata_only", "location": "正文的引证位置；尚待核查原文页码"}
  ]
}
```

学校反馈在本项目记录触发条件、修正前后位置、复验产物和适用的版本；下次遇到同一问题先验证条件，再复用做法。院系的个别例外随项目保存。RWT 沿用现有的登记、检查点与复核活动，不包含外部技能的自动经验库或逐项 Word 样式继承检查器。

运行后用输出中的两份 SHA-256 绑定实际审阅记录。例如，亲自逐页看过某一版三页 PDF 后，可补入以下字段。`note` 是项目中可读的实查记录，其中写明导出引擎与版本、检查者、页码、标题与表格分页、中文缺字、页面问题和处理情况。用真实指纹替换占位文字，`outcome` 取 `clear` 或 `issues`。若模板会改变 Word 与其他引擎的排版，以目标环境实际导出结果再核对。

```json
"visual_review": {
  "note": "review/pages-R02.md",
  "renderer": "本次实际使用的导出引擎及版本",
  "docx_sha256": "实际可编辑稿 SHA-256",
  "pdf_sha256": "实际导出稿 SHA-256",
  "pages": "1-3",
  "outcome": "clear"
}
```

退出码 `0` 表示所配置的可检查项通过，页审记录与版本及页码对应；`1` 表示存在不匹配或输入不可用；`2` 表示存在待核事项。检查器不会启动 Word、导出稿件或替人阅读页面。同一短句在两份文件里出现，也不能单独证明翻译、全文格式、引证或学位办验收通过。只要求 LaTeX、局部润色或单一格式时，直接按相关条款核对，无须为使用脚本生成额外副本。

在持续项目中，将本次稿源、导出物和核验结果按 [RWT 交付指导](../../rw-review/references/submission-delivery.md) 绑定到同一版本。历史结论仅适用于当时文件。作者确认的学校例外及本轮修正保存在项目本地。

此流程独立实现。学校要求与材料用途分开记录、对真实稿件核查、将页面验收绑定文件版本等做法参考了 [thesis-delivery-zh 的固定提交](https://github.com/sanipedro679-gif/thesis-delivery-zh/tree/b851a7a0e3400d2cb95366c6a0e02e35e821c734)。该提交根目录没有许可文件，RWT 提供自己的指引、清单与检查代码。
