# 回复意见与落实修改

把每条意见落实为可核对的判断、修改或解释，再写回复。沿用原审稿人编号和评论标识；复合意见可拆成子项，但保留对应关系，不遗漏难答的部分。

稿件、返修计划和回复信均沿用 `rw-writing` 的直接表达规则。回复先回答具体问题，再给依据、实际处理和位置；执行命令、检查器范围与发布状态集中放入核对记录。计划的未执行状态在开头标明一次，具体受阻项保留在任务表中。

## 按请求选择交付

只要计划时交付返修任务与顺序；只要回复草稿时依据现有材料写回复；核对交付时再检查回复与当前文件。简单意见直接处理，多个相互依赖的任务才展开计划或结构化检查。

## 拆分、取舍与安排

保留每条原意见和来源编号，例如 `R1.C2`；其中两项要求可拆为 `R1.C2.a`、`R1.C2.b`，各自指回原编号。重复要求可共用一次修改，每条原意见仍有对应回复。编辑与审稿人要求冲突时并列记录，并指出需要作者决定的取舍。

分别判断四件事，避免用一个标签替代全部状态：

- **严重度**：`blocking` 是当前明确的交付前置条件；`major` 影响中心主张或主要证据；`minor` 是局部修正；`optional` 是可选扩展。依据具体影响判断。
- **处理决定**：接受、部分接受、澄清、有依据不同意或暂缓；部分接受列清接受和未接受的要求。
- **执行状态**：计划、进行中、受阻或已完成。已有稿件中的澄清标作“核对既有内容”，与本轮新改动分别表达。
- **工作量**：按作者提供的可用时间、依赖、设备或资料估算；未知工作量标待估算。

先列实际前置关系，再安排顺序。例如“确认分析单位 → 重算结果 → 更新表图 → 更新摘要 → 核对回复”；独立的文字修改可以并行。对固定期限给出工时依据、可用总量和缓冲，明确超出的任务与可选取舍。共用改动只计一次工时，各子项分摊实际工作量，独立回复另行估计。没有工时估计时只给依赖顺序；最长依赖链与人员、计算资源约束下的实际完工日期分别处理。

持续执行仍使用原有 `activity.depends_on` 及核心检查；本节的计划是已有返修产物的内容，状态以已登记活动为准。计划中的 `planned`、`in_progress` 分别对应核心活动的 `pending`、`in-progress`；`blocked` 根据实际进度保留为其中一种，在活动 `note` 中写明阻塞原因。只有实际完成时才登记 `done`。计划 JSON 不直接作为活动登记，也不自动同步状态。纯规划与只读核对不增加登记。

## 意见与当前状态对应

在现有回复稿或修订说明中按需要记录：

| 意见 | 判断依据 | 实际修改或处理 | 当前稿件定位 | 验证状态 |
|---|---|---|---|---|
| 保留评论编号及其要求 | 原文、推导、结果、来源或范围依据 | 已完成的改动，或尚待执行的方案 | 实际核对的章节、定理、公式、图表或行号 | 本次真正完成的检查及未完成项 |

这是报告中的工作对应表，不是新的权威台账；已有同类记录可直接复用。材料不齐时先处理已知意见，继续不依赖缺口的工作；只有会改变判断或修改方向的问题才需要澄清。

稿件不可见时可起草可支持的回复，但不能声称已经改稿。仅要求回复草稿时保持原稿不动；已授权修订时再修改相关文件，并保留仍无法解决的缺口。

## 依据问题选择处理方式

- 已核实错误：修复证明、分析或材料，必要时补条件、收缩结论或撤回主张。检查依赖它的摘要、结论、图表与后续论证，不只修被点名的一行。
- 表述或误解：先确认原文能否清楚传达含义，给出直接解释和适当澄清；不以“审稿人误解”代替依据。
- 有理由不同意：用精确命题、反例、原文或研究范围说明理由，区分不属于本文目标的扩展与确实影响中心论证的缺陷。
- 新增工作：先判断其能否解决意见。补证明、补实验、核对新文献或重算结果只有实际完成后才能写成完成；计划和待执行部分保留相应状态。

按稿件实际方法使用 `rw-validation` 或 `rw-literature`。不因一条笼统意见强加实验，不用多写一段解释冒充补证明，也不为迎合意见扩大未受支持的结论。

## 写成可验证的回复

每条回复直接回答问题，给出关键依据、采取的处理和真实位置。较长补证或分析放在合适的稿件或附件，回复保留核心逻辑；少用重复感谢和空泛保证。

交付前逐项核对“已修改、已证明、已计算、已核对”与实际文件或执行证据，在核对记录中分别说明编译、数值重跑、来源核查和内容判断；未确认的位置不编造页码或行号。多份交付材料涉及同一改动时，按需做[跨材料核对](cross-material-consistency.md)。

按原意见和原子子项逐项查覆盖：回复在何处、实际改动在何处、所述结果来自哪个版本。合理的澄清、不同意或暂缓可以没有正文改动，回复须给出理由与当前状态。写“已修改”的项目同时核对当前文本及本轮差异。所有意见都有回复与所有要求都已实施分别统计。

## 可选只读检查

需要计算核对多项依赖、工时或回复定位时，可把现有返修表导出为一份 `revision-plan.json`，使用[检查脚本](../scripts/check_revision_plan.py)。它只读取这份产物和指定目录中的文本，输出检查结果，不运行任务。

```sh
python3 skills/rw-review/scripts/check_revision_plan.py revision-plan.json --root PROJECT
python3 skills/rw-review/scripts/check_revision_plan.py revision-plan.json --root PROJECT --delivery
```

从项目内技能副本使用时，脚本在 `.agents/skills/rw-review/scripts/`。根目录 `PROJECT` 指当前稿件和回复所在目录。结构示例：

```json
{
  "sources": [{"id": "R1.C1", "text": "请交代处理分配和分析单位。"}],
  "items": [{
    "id": "R1.C1.a",
    "source_id": "R1.C1",
    "severity": "major",
    "decision": "accept",
    "status": "planned",
    "depends_on": [],
    "effort_hours": 2
  }],
  "available_hours": 3
}
```

`decision` 使用 `accept/partial/clarify/decline/defer`，`status` 使用 `planned/in_progress/blocked/done`。每个实际子项单列，`depends_on` 指其他子项 ID。有时限时用 `available_hours` 填可用工作量，未知估时省略；缓冲由作者在可用额度中预留。脚本返回依赖批次、已知工时与未知项，提示遗漏原意见、依赖环和预算问题。

核对回复时，为各子项提供 `reply: {"path": "response.md", "quote": "唯一出现的实际回复摘录"}`；实际修改用 `changes` 数组保存同样的定位对象。路径相对 `--root`，摘录必须在该文本中唯一出现。`--delivery` 要求逐项有回复；已完成且接受／部分接受的项目还要有修改定位，澄清／不同意／暂缓须有 `reason`。未完成、暂缓和不同意的项目分别返回。

检查针对所列意见、依赖和文本位置；正文含义、修改是否解决意见，以及原意见是否完整录入，仍对照原材料审阅。只读检查的通过结果不改变任何活动状态。正文沿用 `rw-writing` 的直接表达规则。

交付完整回复和仍需完成的事项。需要持续跟踪时，用既有 `artifact`、`activity` 和显式版本规则保存实际产物与进度；回复草稿或修订报告不改变外部投稿状态，也不自动联系编辑或审稿人。
